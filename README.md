# 乡宿通 · 乡村民宿旺季运营平台

节假日同时承接 **官网 / 微信小程序 / OTA（携程、美团）/ 电话** 订房的乡村民宿，用一个系统把
**统一房态与价格 → 入住人数/宠物/加床/早餐/押金/发票 → 到店前保洁·布草·维修排班 → 厨房备餐 →
八类旺季异常 → 差评归因 → 补偿与押金扣除 → 结算 → 旺季复盘 → 下一轮排房调价** 串在同一条住宿链路里。

技术栈：React 18 + Vite + TypeScript + Ant Design 5 ｜ NestJS 10 + TypeORM ｜ PostgreSQL 15 ｜ Docker Compose。

---

## 一、一键启动（Docker Compose，推荐）

前置：已安装 Docker 与 Docker Compose v2。

```bash
cp .env.example .env      # 可按需改端口/密码/JWT 密钥
docker compose up -d --build
```

- 前端（含 nginx 反向代理 /api）： http://localhost:8080
- 后端 API 基址： http://localhost:3000/api
- 健康检查： http://localhost:3000/api/health
- PostgreSQL： 本机 5432（账号见 .env，默认 postgres/postgres，库名 homestay）

首次启动后端会自动建表并写入**旺季演示数据**（3 个房型、7 间房、5 个渠道、11 笔订单、
含超卖/布草延迟/早餐不足/空调故障/宠物损坏/差评补偿的完整链路）。重置演示数据：

```bash
docker compose down -v && docker compose up -d --build
```

## 二、本地开发启动（无 Docker 时）

需要 Node.js 20+ 与可连通的 PostgreSQL 15。

```bash
# 1. 数据库
createdb -U postgres homestay

# 2. 后端（端口 3000）
cd backend
npm install
DB_HOST=127.0.0.1 DB_PORT=5432 DB_USER=postgres DB_PASSWORD=postgres \
DB_NAME=homestay JWT_SECRET=dev-secret npm run dev
#   生产方式：npm run build && node dist/main.js

# 3. 前端（端口 5173，vite 已配置 /api 代理到 127.0.0.1:3000）
cd ../frontend
npm install
npm run dev
```

## 四、核心业务链路与页面

| 模块 | 说明 |
| --- | --- |
| 旺季总览 | 今日在住/到离店、各房型出租率、保洁与早餐任务、布草库存、忌口提醒、未闭环异常 |
| 房态与排房 | 五渠道**共用同一库存池**的房态日历（物理房/可售/维修封锁/已订/超卖），以及下轮节假日排房调价建议一键落地 |
| 订单与住宿链路 | 多渠道登记（人数、宠物、加床、早餐份数、忌口、押金、发票），订单详情同屏串联保洁、布草、维修、早餐、异常、差评、补偿、结算 |
| 保洁与布草 | 按离店日自动生成保洁任务与布草申领；送达扣减干净库存、打扫完成转洗涤、回库恢复；延迟退房/布草延迟自动阻塞打扫 |
| 早餐厨房 | 按供应日汇总份数与忌口（如花生过敏）；「供应不足」自动生成异常进入补偿链路 |
| 维修房态 | 硬件故障报修自动封锁房态并入事件链，完工自动恢复房态、关闭事件 |
| 异常事件中心 | 八类异常统一收口：延迟退房、房间硬件故障、布草未送达、临时加人、宠物损坏、早餐不足、渠道超卖、差评 |
| 差评与补偿 | 差评四类归因（硬件/服务/超卖/餐食），按未闭环事件给补偿建议（券/退款/升级/现金/押金扣除），押金扣除有超额校验 |
| 结算单 | 房费、加床、早餐、加人/宠物、渠道佣金、押金收取与扣除、退款、补偿券、现金赔付、应收与净收入一单清 |
| 旺季复盘 | 按渠道/房型的 ADR、佣金率、补偿成本、净利率；差评归因分布；异常结构；自动定性「价格策略问题 / 履约能力问题 / 个别客诉」 |

### 下一轮排房规则（复盘 → 排房的闭环）

- 发生超卖但无履约事故 → 需求旺盛，**提价 12%，不削房量**；
- 布草延迟 ≥2 次或早餐不足 ≥2 次 → **每类短板调减 1 间可售房**（上限物理房一半）留打扫/备餐缓冲，价格 +5%；
- 入住率 ≥90% 且履约稳定 → 提价 10%；入住率 <60% → 降价 10% 引流；
- 建议在「房态与排房 → 下轮排房建议」预览后一键写入 `inventory_days` 可售房量日历。

## 五、建议的业务验证路径（对照演示数据）

1. 用 `owner` 登录，总览页可见今日未闭环异常与山景房满房；
2. 打开「房态与排房」：山景大床房 3 间已订 4（含 1 单携程强制超卖，红色标记）；尝试普通下单会被库存拦截；
3. 进入超卖订单（郑凯）：未分房不能入住 → 取消电话订单（吴姐）释放 A102 → 给超卖单分房 → 办理入住；
4. 「保洁与布草」：赵晓离店的 A102 因布草未送达阻塞 → 送达布草（库存扣减、阻塞解除、事件关闭）→ 完成打扫（布草转洗涤）→ 洗涤回库；
5. 「早餐厨房」：看到孩子花生过敏等忌口；把赵晓的早餐标记为「供应不足」，自动生成异常；
6. 订单详情内登记「临时加人」（附加费 100 元/人/晚自动重算）、「宠物损坏」（自动开维修单并建议押金扣除，超额扣除会被拦截）；
7. 差评页：王磊 2 星「空调半夜坏了」自动归因为**硬件**，可改归因、回复、发补偿券；
8. 赵晓订单：「智能补偿建议」→ 一键发放早餐退款 + 差评券 → 生成结算单，核对房费/早餐/佣金/券/退款/净收入；
9. 「旺季复盘」：看渠道（携程 12% 佣金后净利率）、房型利润、差评四类归因、异常结构与每房型问题定性；
10. 回到「房态与排房 → 下轮排房建议」：山景房因超卖给出提价建议，采纳后写入下轮可售房量。
